SPRINT 4
--------------------------------
The objective of Sprint 4 was to implement communication between FreeRTOS tasks using queues instead of relying on global variables to transfer sensor and control data. Additionally, this sprint introduced our physical actuator, a buzzer controlled through a PWM signal, whose frequency changes according to the inventory status determined by the control task. This sprint was separated into 2 different sections:

1. Implement FreeRTOS queues to transfer sensor measurements and control states between tasks.
2. Configure and deploy control task using buzzer, and implement FreeRTOS queues to transfer control states between tasks.

Sprint 4 began by cloning the previous sprint's project, then I included the queue.h library to access the FreeRTOS queue functions. Before implementing the queues, four structures were defined to organize the information being transferred between tasks: weight_grams, uart_output, weight_level, and status_level. Subsequently, four queue handles were declared using QueueHandle_t and initialized using xQueueCreate(), specifying a capacity of four elements and the size of the corresponding structure. The weight_queue was created to transfer calibrated weight measurements from SensorTask to ControlTask, using xQueueSend() and xQueueReceive() to send and retrieve the data. Similarly, uart_queue was implemented to transfer the same weight measurements from SensorTask to MessageTask for serial monitoring. Additionally, status_queue was introduced to transfer the inventory status generated by ControlTask to MessageTask, allowing the appropriate UART message to be selected based on whether the inventory was normal, running low, or empty. Finally, level_queue was implemented to independently transfer the same control status to ActuatorTask, allowing the buzzer to respond without competing with the UART task for the same queue messages. Laslty, by using data from queus we implemented our pysichal actuator,I configured TIM3 Channel 2 to generate a PWM signal, allowing the buzzer's pitch to be adjusted by changing the output frequency. The actuator control logic was implemented using the three states established in the previous sprint: state 0 disables the buzzer during normal operation, state 1 generates a lower-frequency tone when inventory falls below 20%, and state 2 generates a higher-frequency tone when inventory falls below 10%. This allowed the system to provide an audible indication of the current inventory condition while continuing to transmit weight and status information through UART.

**Testing and Results**

During the initial testing, the system was configured with two queues to transfer information between the four tasks. However, I encountered communication issues because both the actuator and UART, and UART and Control messaging tasks attempted to receive control-state information from the same status queue and weight queue. Since receiving an item from a FreeRTOS queue removes it, the tasks effectively competed for the available messages, causing one task to miss updates or remain waiting for information required to execute its intended functionality. To resolve this issue, I introduced a two new queues to separate the communication paths and ensure each receiving task obtained its own copy of the required data.  This separation resolved the competing-consumer issue and allowed both the UART messaging and buzzer control functions to respond to the inventory states independently. The resulting system demonstrated the integration of FreeRTOS queue-based communication with PWM actuator control, providing both audible warnings and serial monitoring based on the measured inventory level.

SPRINT 5
--------------------------------

The objective of Sprint 5 was to implement synchronization mechanisms using FreeRTOS binary semaphores and mutexes to improve communication and resource management between tasks, and help us deal with our previous communication collision in a more optimized professional way. Building on the previous sprint's queue implementation, this sprint introduced a dedicated logging task responsible for collecting system information and transmitting it through UART while preventing multiple tasks from accessing the serial peripheral simultaneously. This Sprint was devided in 2 sections:

Part 1: Logging Task and Binary Semaphore
Part 2: UART Mutex Implementation

Sprint 5 began by cloning the previous sprint's project and modifying the existing task structure to improve how UART messages were generated and transmitted. In the previous sprint, 'MessageTask' received weight measurements and inventory status values through separate queues and then processed these values to determine which message should be displayed. In this sprint, I redesigned this approach by replacing this task with an improved 'LogginTask'. The main difference in this implementation is that each task is now responsible for generating its own formatted messages, while 'LogginTask' is responsible only for receiving and transmitting them through UART. To accomplish this, I defined a new structure called LogMessage_t, containing a character array for storing formatted messages, and created a dedicated queue named LogQueu. The sensor task generates messages containing weight measurements, the monitoring task generates messages when the inventory status changes, and the actuator task generates messages containing the current buzzer state and frequency. These messages are sent to LogQueu, either directly or through the Postlog helper function. Additionally, I implemented a binary semaphore named Logsemaphore using 'xsempaphorecreateBinary()' to notify the logging task whenever a new message becomes available, rather than relying on previous educated guess task delays. After successfully adding a message to the queue, the corresponding task signals the semaphore using xSempahoreGive(). 

The second part of Sprint 5 focused on protecting the UART peripheral from simultaneous access by multiple FreeRTOS tasks. Since both the logging task and actuator task could transmit messages through USART2, a mutex named logMutex was created using xSemaphoreCreateMutex(). Before transmitting information, each task must successfully acquire the mutex using xSemaphoreTake(), ensuring exclusive access to the UART peripheral, to avoid the problem we had in sprint 4. Once the message has been transmitted using HAL_UART_Transmit(), the mutex is released using xSemaphoreGive(), allowing another task to access the same resource.

***Testing and Results***

Testing for Sprint 5 focused on verifying the operation of the binary semaphore and mutex through UART communication using Tera Term. The logging system was configured to display sensor measurements, inventory status changes, and actuator information generated by the different FreeRTOS tasks. To evaluate semaphore functionality, I disable the operation of xSemaphoreGive() temporarily disabled to observe whether the logging task remained blocked without receiving a notification, which it did, thus confirming the operation of our binary sempahore, then restored to confirm that new messages were processed again. Similarly, mutex functionality could be evaluated by comparing UART transmissions with and without mutex protection while both the actuator and logging tasks attempted to transmit information, once the xSemaphoreGive() was commented, the terminal only printed the UART message of the task with highest priority only 1 since the task took the mutex and never gave it back. In our case our highest priority Task was our Actuator, so essentially, we could only get actuator updates, no weight readings or anything else.
